# DeepSeek Harness 全书总览：它究竟是怎么工作的

> 面向第一次系统了解 DeepSeek Harness（`dsh`）的总览。它不替代源码或逐章教程，目标是先建立一张「全局地图」：**dsh 要解决什么问题、内部有哪些层、一次任务怎样跑完，以及应该如何学习和扩展它。**
>
> 相关笔记：[[DeepSeek harness]]、[[DeepSeek harness 架构总结]]、[[DeepSeek Harness 高层结构图]]。

## 先说结论：dsh 不是一个聊天界面，而是一套 Agent 的「操作系统 / 装配线」

大模型本身可以理解文字、生成文字，但它不会天然读文件、运行命令、搜索网页、保存状态或等待人的批准。

一个真正能做事的 Agent，至少还需要：

- **大脑**：向 LLM 发请求、接收流式输出；
- **手和感官**：文件、终端、浏览器、代码运行、MCP 等工具；
- **工作流程**：决定何时继续思考、何时调用工具、何时结束；
- **记忆与记录**：把对话和工具结果可靠保存下来，以便恢复和回放；
- **安全边界**：权限、审批、沙箱；
- **对外形态**：CLI、Web、编辑器或其他应用接入。

**DeepSeek Harness（dsh）就是把这些部件组装、运行和替换的框架。**

它不是「某个固定的 DeepSeek 聊天产品」。你可以把 DeepSeek 换成其他模型，把本地 Bash 换成远程沙箱，把 Web UI 换成 CLI 或自己的应用，也可以加入新的工具、工作流和子 Agent。

## 它最重要的设计：一切皆插件

理解 dsh 的钥匙只有一句话：**Everything is a plugin（一切皆插件）。**

在很多程序里，Agent 循环、工具系统、模型适配器是难以触及的「核心」；想替换它们，往往只能改源码、打补丁或 fork 项目。dsh 反过来设计：连这些东西都作为插件挂入运行时。

底层的 **Cordis** 负责提供一个共享的 `Context`（上下文 / 服务总线）。插件可以向这个 Context 注册：

- **Service（服务）**：例如 `ctx.llm`、`ctx.fs`、`ctx.tools`；
- **Event（事件）**：在请求、工具执行、会话写入等关键时刻插入行为；
- **Effect（可逆注册）**：插件卸载时，它注册的内容会跟着撤销。

因此，dsh 的扩展思路不是「改一个巨型主程序」，而是：**选择一个服务或事件扩展点，挂上一个插件。**

## 用「大脑、手、管家、日记本、门卫、外壳」记住全书

这套教程的 14 章看似很多，实际上都可以归入六个角色：

| 角色           | dsh 中对应内容                                      | 解决的问题                   |
| ------------ | ---------------------------------------------- | ----------------------- |
| **大脑**       | LLM、系统提示词、上下文                                  | 用哪个模型、给模型看什么、如何取得流式回答   |
| **手和感官**     | tools、shell、fs、web、LSP、MCP、terminal            | Agent 能做哪些事、能接触哪些外部世界   |
| **管家 / 调度员** | agent-loop、subagent、workflow、todo、plan、jobs    | 一项任务怎样拆解、循环、委派和收尾       |
| **日记本 / 记忆** | session、storage、workspace、settings、credentials | 对话和状态怎样保存、恢复、查询及投影      |
| **门卫**       | sandbox、approval、permission、ask-user、guard     | 哪些操作可执行、哪些需要用户确认、怎样避免失控 |
| **外壳 / 接口**  | bundle、profile、CLI、Web GUI、SDK、ACP、API         | 怎样启动、组合成产品，并让外部应用使用它    |

后面所有包和概念，本质上都是在补齐这六类职责。

## 一次「让 Agent 完成任务」的完整旅程

假设你对 dsh 说：**「检查这个项目的报错，修好后告诉我改了什么。」**

大体会发生如下流程：

1. **输入进入会话**
   - UI、CLI 或 API 把你的消息送入某个 session。
   - session 不只是聊天记录，也是后续恢复、fork、回放的事实来源。

2. **Agent 循环认领任务，组装上下文**
   - 系统提示词、历史消息、当前注入的上下文、可用工具的 schema 被组合为模型请求。
   - 这叫一个 **step** 的开始。

3. **LLM 思考并决定是否调用工具**
   - 模型可能先请求读取报错日志、列出目录、运行测试。
   - 模型输出是流式的，因此 UI 可以一边生成一边展示。

4. **工具执行受到能力和权限约束**
   - 工具通过 `ctx.tools` 暴露；例如 Bash 工具背后会使用 shell/subprocess 能力。
   - 文件访问、命令执行可能经过 sandbox、审批和策略检查。

5. **工具结果写回会话，进入下一步**
   - Agent 将结果带回给模型，开始下一次模型请求。
   - 模型可能继续读文件、改代码、跑测试；这会形成多个 step。

6. **没有待办时，一轮任务结束**
   - 多个 step 合起来叫一个 **turn**。
   - 最终文本回答、每次工具调用和关键状态都已被写入 session 日志。

可以把它压缩成这条链：

> 用户输入 → Agent 组装上下文 → LLM 决策 → 工具执行（受权限/沙箱约束）→ 结果进入日志 → LLM 再决策 → 任务结束

这里有一条极重要的规则：

> **模型所见的内容，必须能从会话日志重建。**

所以日志不是附属功能，而是 Agent 的「事实底座」：恢复会话、生成 transcript、fork 一个分支、遥测分析都依赖同一条记录流。

## 为什么总在说 Seam（能力接缝）？

dsh 不只是把功能做成插件，还把每一种可替换能力抽成一个 **Capability Seam（能力接缝）**。一个接缝通常有三方：

1. **Service Definition**：声明一个稳定的能力接口，例如 `ctx.shell`；
2. **Service Provider**：提供具体实现，例如本地 Bash 或沙箱内 Bash；
3. **Consumer**：使用它的组件，例如暴露给模型的 `bash` 工具。

以执行命令为例：

```text
Agent / bash 工具（Consumer）
          ↓ 使用 ctx.shell
Shell 接口（Service Definition）
          ↑ 可替换实现
本地 Bash / PowerShell / 远程沙箱（Provider）
```

好处是：工具本身不需要知道命令是在本机还是远端跑。把 provider 换成沙箱后，所有依赖这套执行环境的能力都可以一起迁移。这就是 dsh 的模块化不止停留在「代码分文件」，而是落实为「能力实现可替换」的原因。

## Profile、Bundle、Preset：三个「配置组合」别混淆

这三个词很像，可这样区分：

- **Bundle**：一包可复用的「插件配置 + 代码」，例如基础能力包或 Web UI 包。
- **Profile**：一个完整运行方案，指定要叠加哪些 bundle，再叠上用户自己的 patch。`web`、`headless` 是常见形态。
- **Preset**：更偏向「某个会话 / Agent 应该用什么能力集合」的配方。例如一个只允许读文件的 Agent，与一个可以运行终端的编码 Agent，可以使用不同 preset。

类比为：

> Bundle 是食材包；Profile 是整家餐厅的菜单与装修方案；Preset 是某一份具体套餐。

配置是按层叠加的，越上层优先级越高。因此你通常不必改官方 bundle，只要以 patch 覆盖对应的配置行即可。

## dsh 适合什么，不适合什么？

它适合：

- 想搭建**有工具调用、权限控制、持久会话**的 Agent；
- 想把模型、执行环境、工具服务做成**可替换模块**；
- 想开发 CLI、Web、ACP、JSON-RPC 等多种接入形态；
- 想深入理解或扩展 DeepSeek Harness 本身。

它不一定适合：

- 只想做一次简单的「Prompt → 回答」调用；
- 不需要工具、会话、权限或多轮流程；
- 不愿面对 TypeScript、插件运行时和快速演进的开发者预览 API。

换句话说：dsh 的价值不在于用最少代码调一次模型，而在于**把复杂 Agent 系统拆成可以组合、替换、治理和演进的零件**。

## 第一次学习时，最值得抓住的五件事

1. **dsh 是框架，不是单一聊天产品。**它负责装配 Agent 的能力。
2. **插件和 Cordis Context 是根基。**后面的所有包都围绕服务、事件和 effect 协作。
3. **Seam = 稳定接口 + 可替换实现 + 使用者。**它解释了 dsh 的可替换性。
4. **Turn 由多个 Step 组成。**一次模型请求加工具调用是 step；直到没有待办才结束 turn。
5. **日志是事实来源。**模型看到什么、会话如何恢复和回放，最终都绕不开 session log。

只要先握住这五点，后续遇到 `ctx.xxx`、provider、consumer、session event、bundle patch 等术语，就不会觉得它们是零散的黑话。

## 补充：从官方资料看，怎样把这张地图落到实际体验

为避免只停留在抽象概念，可以用官方 README 给出的最短路径亲自观察 dsh 的「外壳」：安装 Node.js 后运行：

```shell
npx @deepseek-ai/dsh web
```

它会默认在 `http://127.0.0.1:3080` 启动 Web UI。此时看到的网页只是一个接入形态，而不是 dsh 的全部：网页把消息交给底层 session 和 agent-loop；agent-loop 调模型和工具；权限、沙箱、日志及插件配置仍在背后发挥作用。

因此，可以把 dsh 分成两层来理解：

- **你直接看到的产品层**：Web UI、CLI、ACP、SDK/API——负责把人或其他程序接进来；
- **真正可复用的 Harness 层**：Cordis、插件、能力接缝、Agent 循环、会话与权限——负责让 Agent 安全且可组合地完成工作。

官方仓库也将 dsh 明确标为 **Developer Preview**，并警告会有破坏性兼容变更。所以本篇适合用来建立长期有效的架构心智模型；实际安装命令、配置字段和插件 API，则应在动手前回到官方文档核对。
