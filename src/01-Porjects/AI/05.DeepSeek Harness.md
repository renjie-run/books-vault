# DeepSeek Harness：从总览到架构的通俗理解

> DeepSeek Harness（简称 `dsh`）不是一个固定的聊天应用，而是一套用来**组装、运行、扩展和治理 AI Agent** 的开源框架。它的核心口号是：**Everything is a Plugin（一切皆插件）**。

## 高层结构图

![[assets/DeepSeek Harness/DeepSeek Harness 高层结构图.excalidraw]]

图中概括了接入层、Agent Loop、Cordis 插件运行时、可替换的能力接缝、外部执行环境，以及以 Session Log 为事实底座的关系。

## 0. 先用一句话理解它

普通的大模型只会「理解和生成文本」；一个能真正完成任务的 AI，还要会读写文件、运行命令、搜索网页、记住上下文、请求授权，并能安全地持续工作。

**dsh 就是一套把这些能力装配起来的 Agent 基础设施。**

可以把它看作 Agent 的「操作系统」或「装配线」：

```text
用户 / 外部程序
      ↓
Web UI、CLI、SDK、ACP、API       ← 接入层（外壳）
      ↓
Agent Loop                       ← 调度：思考、调用工具、继续或结束
      ↓
LLM + 工具 + 会话日志 + 权限/沙箱 ← 可替换的核心能力
      ↓
文件、终端、网页、MCP、远程沙箱等外部世界
```

因此，dsh 不是只能服务 DeepSeek 模型的「聊天壳」。理论上可以替换模型适配器、执行环境、工具、UI 或接入方式，组装出自己的编码 Agent、研究 Agent、自动化工作流或嵌入式 Agent 服务。

---

## 1. 为什么需要 Harness，而不只是直接调模型 API？

若只是做一次「输入 Prompt → 获取回答」，直接调用模型 API 就足够。

但当需求变为：

- 读取项目代码、运行测试、修改文件；
- 调网页或 MCP 服务获取信息；
- 工具执行前询问用户是否允许；
- 中断后恢复任务、回看全过程；
- 把复杂任务分给子 Agent；
- 让同一套能力同时供 CLI、Web 和编辑器使用；

问题就不再是「如何调用模型」，而是「如何稳定地运行一个 Agent 系统」。dsh 处理的正是后一类问题。

用六个角色可以概括它的完整职责：

| 角色 | dsh 中的代表模块 | 解决的问题 |
|---|---|---|
| **大脑** | LLM、system prompt、context | 选用哪个模型，模型看见什么，如何流式输出 |
| **手和感官** | tools、shell、fs、web、LSP、MCP、terminal | Agent 能做什么、接触什么外部世界 |
| **管家 / 调度员** | agent-loop、subagent、workflow、todo、plan、jobs | 任务如何循环、拆分、委派、收尾 |
| **日记本 / 记忆** | session、storage、workspace、settings、credentials | 如何保存、恢复、查询会话与运行状态 |
| **门卫** | sandbox、approval、permission、ask-user、guard | 哪些操作允许执行、哪些要人工批准 |
| **外壳 / 接口** | profile、bundle、CLI、Web、SDK、ACP、API | 如何启动、组合成产品、接入外部应用 |

## 2. 核心原则：一切皆插件

dsh 基于 **Cordis** 运行时。可以把 Cordis 想成一个共享的「服务总线」——所有插件围绕同一个 `Context`（上下文）协作。

插件主要能贡献三类东西：

- **Service（服务）**：一项可被其他模块使用的能力，例如 `ctx.llm`、`ctx.fs`、`ctx.tools`；
- **Event（事件）**：在请求模型、执行工具、写入会话等时机插入逻辑；
- **Effect（可逆注册）**：插件挂载时注册能力，卸载时自动撤销注册。

这意味着 dsh 中没有很多不可触碰的「神圣核心」：模型适配器、工具注册表、会话记录，甚至 Agent 循环本身都以插件方式组成。

> 类比：它不是焊死的一辆车，而是一套乐高。你不必把整辆车拆掉重造，只要换掉模型、工具或执行环境对应的积木。

## 3. Capability Seam：为什么「换实现」会影响整块能力？

dsh 将可替换能力设计为 **Capability Seam（能力接缝）**。每个接缝由三种角色构成：

| 角色 | 含义 | Shell 例子 |
|---|---|---|
| **Service Definition** | 声明稳定接口，通常对应一个 `ctx.<key>` | `dsh-shell` / `ctx.shell` |
| **Service Provider** | 接口的具体实现 | 本地 Bash、沙箱 Bash、PowerShell |
| **Consumer** | 注入并使用服务的模块，常常是模型可调用工具 | `dsh-tool-bash` |

```text
Agent / bash 工具（Consumer）
          ↓ 使用 ctx.shell
Shell 接口（Service Definition）
          ↑ 可替换实现
本地 Bash / PowerShell / 远程沙箱（Provider）
```

例如，把 shell、文件系统、子进程的 provider 从本地实现换成远程沙箱实现，依赖这些能力的 Bash、终端、LSP 等功能就会进入同一个新执行世界。Consumer 不需要分别为「本地版」和「沙箱版」重写。

> 类比：接口是插座，Provider 是不同的供电实现，Consumer 是电器。插座标准不变，换供电方式时电器仍可工作。

## 4. 运行配置：Bundle、Profile、Preset 不要混淆

运行中的 dsh 不是单一程序，而是一棵由配置叠出来的「插件树」。三个相近概念可以这样记：

- **Bundle**：一包可复用的「插件配置 + 代码」，例如基础能力包、Web UI 包；
- **Profile**：完整的运行方案，决定叠加哪些 Bundle，并加入用户自己的补丁；常见形态如 `web`、`headless`；
- **Preset**：某个 Agent / 会话应该拥有哪一组能力的配方。例如只读 Agent 与可以运行终端的编码 Agent 可以使用不同 preset。

类比：**Bundle 是食材包，Profile 是一家餐厅的菜单和装修方案，Preset 是具体的一份套餐。**

配置按层应用，越上层优先级越高：

```text
Bundle（按 Profile 中的顺序）
  → Profile 自己的 cordis.patch.yml
    → home 级补丁
      → --patch 命令行覆盖层
```

所以定制时通常不必直接改官方配置：可以通过 patch 按 row id 覆盖或插入配置行。查看当前实际加载的插件树：

```shell
dsh --profile web --dump-config
```

## 5. 一项任务在 dsh 内部怎样跑完？

假设用户提出：「检查项目报错，修好后说明改了什么。」

1. **输入进入 Session**：UI、CLI 或 API 把消息写入会话；
2. **Agent 认领输入**：组装系统提示词、历史消息、注入上下文和可用工具 schema；
3. **LLM 请求**：模型分析任务，可能决定调用工具；
4. **工具执行**：例如读取文件、运行命令、搜索网页；执行会经过权限、审批、沙箱或策略；
5. **结果回写日志**：工具结果进入会话，再带给模型进行下一次决策；
6. **循环直至结束**：模型可能继续改代码、跑测试；没有待办时任务收尾。

```text
用户输入
  → Agent 组装上下文
  → LLM 决策
  → 工具执行（权限 / 审批 / 沙箱）
  → 结果写入 Session Log
  → LLM 再决策
  → 直到任务结束
```

这里有两个必须掌握的术语：

- **Step（步骤）**：一次模型请求，加上该次请求引发的工具调用；
- **Turn（轮次）**：由零到多个 Step 构成，从认领一条输入到没有待办时结束。

也就是说，一句用户请求不一定只请求一次模型：模型读日志、调用工具、收到结果、继续判断，可能往复多个 Step。

## 6. Session Log：为什么它是 Agent 的事实底座？

dsh 的一条关键不变式是：

> **模型所见 ⟺ 已入日志。**任何送进模型请求的内容，都必须能够从 Session Log 重建。

这不是单纯为了保存聊天记录，而是让同一份事实流能支撑：

- 会话恢复（resume）；
- 回放与 transcript；
- fork 出会话分支；
- UI 渲染；
- 持久化与查询；
- 遥测和调试。

因此，如果扩展功能想让模型在后续请求里看到新的信息，正确的设计通常是：**把它变成 Session 事件并从日志渲染**，而不是只在内存里临时塞一段文本。

---

## 7. 事件：把新行为插到正确位置

事件是 dsh 的主要扩展点，可大致分三类：

- **Session 事件**：持久化事实，写入日志，重启/回放后仍可存在；
- **Agent 事件**（如 `agent/*`）：观察或拦截正在运行的 Agent 工作；
- **Capability 事件**（如 `fs/*`、`tools/*`）：把策略与适配器挂在某项能力上，不必改 Agent 循环。

如果目的是拦截模型请求或工具执行，通常看 `agent/*`、`tools/*`；如果目的是让某条信息成为可恢复的模型上下文，应使用 Session 事件。选对事件域，比一开始钻进实现细节更重要。

### 第一段：运行基础与 Agent 循环（第 0–4 章）

先理解 Agent、大脑/工具、总体架构、Profile/Bundle 和 Cordis；然后进入 session、system prompt、tools、agent-loop 的核心循环。

**要回答的问题**：dsh 为什么能运行，一次任务怎样在内部流动？

### 第二段：模型与工具能力（第 5–7 章）

学习 LLM 消息与流式响应、`LlmAdapter`；再看 shell、子进程、终端、沙箱、文件系统、LSP、skill、web、MCP、附件等。

**要回答的问题**：Agent 的大脑怎么接模型，手和感官有哪些？

### 第三段：复杂任务与人机协作（第 8–10 章）

学习子 Agent、workflow、todo、plan、goal、job、上下文压缩；以及命令、审批、权限预设、ask-user、会话持久化、设置和凭据。

**要回答的问题**：复杂工作怎样拆解，怎样受控地交给人确认，又怎样可靠保存？

学习启动、Bundle、Profile、Preset、扩展；再看 API、SDK、ACP、Web GUI，以及如何加工具、Provider、模型适配器、聊天节点和测试。

## 9. 常见需求该往哪里扩展？

| 目标 | 优先查看的扩展点 |
|---|---|
| 接一个新模型提供方 | 在 `ctx.llm` 注册适配器 / 实现 LLM Provider |
| 增加模型可调用工具 | 注册到 `ctx.tools`，让 schema 进入 prompt 组装 |
| 增加 Shell 执行环境 | 注册 `ctx.shell` Provider |
| 改变文件访问或策略 | 替换 `ctx.fs` Provider，或监听 `fs/*` |
| 拦截模型请求、工具或 Turn | 使用 `agent/*` 或 `tools/*` 事件 |
| 注入后续模型可见上下文 | `agent.inject()`；若需持久化，设计对应 Session 事件 |
| 增加人类命令或审批 | `ctx.commands`、interaction / approval / permission 相关能力 |
| 增加后台任务 | `ctx.jobs` 与相关工具 |
| 接入自己的产品 | API、SDK、ACP、Web GUI / hooks |

## 10. 实际使用入口与注意事项

官方 README 给出的快速体验方式是：

```shell
npx @deepseek-ai/dsh web
```

默认会在 `http://127.0.0.1:3080` 启动 Web UI。这里的 Web UI 只是「外壳 / 接入层」；它背后仍然是上述插件、会话、Agent Loop、工具、权限与沙箱共同运行。

dsh 目前仍是 **Developer Preview**：接口、配置字段和插件 API 会快速演进，且可能有破坏性变更。因此：

- 用本文建立稳定的架构心智模型；
- 需要写代码、安装或配置时，以官方当前源码和文档为准；
- 初学时优先运行 `--dump-config`，观察实际插件树，再回头对照本文理解。

## 最后用五句话复习

1. **dsh 是 Agent Harness，不只是聊天应用。**
2. **Cordis + 插件** 是它的运行和扩展基础。
3. **Seam = 接口 + Provider + Consumer**，所以能力可以替换实现。
4. **Turn 由多个 Step 组成**，模型与工具通过循环完成任务。
5. **Session Log 是事实来源**：模型看见的内容必须能从日志重建。
